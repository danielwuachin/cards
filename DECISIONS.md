# Architecture Decision Records (ADR)

This document outlines the core architectural and technical decisions made during the development of the Cards API, focusing on security, scalability, and the KISS (Keep It Simple, Stupid) principle.

## 1. Infrastructure & Hosting (AWS ECS Fargate)
**Context:** We needed a highly available REST service behind an Application Load Balancer (ALB) with at least 2 replicas.
**Decision:** We chose AWS ECS with AWS Fargate.
**Rationale:** 
- **Serverless Compute:** Fargate removes the operational overhead of managing underlying EC2 instances. 
- **Rolling Updates (Zero Downtime):** ECS provides native circuit breakers and rolling deployments. If a bad version is deployed, the ALB health checks (`/health`) will fail, and ECS will automatically rollback to the previous immutable task definition without affecting production traffic.
- **Private Subnets:** All containers and the RDS database reside in private subnets. Only the ALB is exposed to the internet, enforcing strict perimeter security.

## 2. Infrastructure as Code (Terraform) & GitOps
**Context:** The deployment process needed to be automated, secure, and reproducible.
**Decision:** We used Terraform to provision all AWS resources and GitHub Actions for CI/CD.
**Rationale:**
- **Single Source of Truth (SSOT) for Secrets:** Instead of hardcoding passwords in GitHub Secrets and manually copying them to AWS, we used Terraform's `random` provider to generate the `db_password` (16 chars) and the `CARD_ENCRYPTION_KEY` (32 bytes hex). Terraform injects these directly into AWS Secrets Manager and the RDS instance. GitHub Actions never sees these credentials.
- **GitOps Pipeline:** A push to `main` triggers a pipeline that runs linters, unit tests, builds the Docker image (using a multi-stage `pnpm@9` build), pushes to Amazon ECR, and automatically updates the ECS service.

## 3. Cryptography & Data Security (AES-256-GCM)
**Context:** The PAN (Primary Account Number) must be stored in a way that's recoverable (not hashed) but never exposed in plaintext, per PCI-DSS.
**Decision:** We implemented symmetric encryption using the `AES-256-GCM` algorithm — encryption, not tokenization or hashing.
**Rationale:**
- **Why GCM?** Galois/Counter Mode provides both confidentiality and data authenticity. It generates an `auth_tag` that acts as a cryptographic checksum. If an attacker with DB write access modifies the ciphertext, decryption fails instead of silently returning corrupted data.
- **Why an IV, and why it isn't a "salt":** These solve different problems. A salt belongs to password *hashing* (bcrypt, PBKDF2) — it stops precomputed rainbow-table attacks on a one-way function. We're not hashing, we're encrypting something we need to read back later, so salts don't apply here. What we need instead is an IV (Initialization Vector — the random per-operation input a block cipher mixes in alongside the key). Its job: encrypting the same PAN twice with the same key must never produce the same ciphertext, or an attacker could spot which rows hold identical card numbers without decrypting anything. We generate a fresh 12-byte IV (`crypto.randomBytes(12)`) on every `encryptPan` call and store it next to the ciphertext — it doesn't need to be secret, only unique per row.
- **AAD binds ciphertext to its row:** We also pass the card's UUID as Additional Authenticated Data (AAD) into the cipher. This means a ciphertext can only be decrypted successfully next to the exact `id` it was created with — if someone copies `encrypted_pan`/`iv`/`auth_tag` from one row into another, decryption fails instead of quietly returning the wrong card's number.
- **Key isolation:** The encryption key never touches the database. It's generated by Terraform, stored in Secrets Manager, and injected into the container as an environment variable at boot. A stolen database dump is unreadable without it.

## 4. Idempotency (RFC 9530 Draft)
**Context:** Payment and card creation endpoints must safely handle network retries without creating duplicate records. This matters more than usual here because the `cards` table deliberately has no uniqueness constraint on PAN — a global unique constraint would let an attacker probe `POST /cards` with guessed numbers and learn which ones already exist from the response (a 409 leaks existence), so duplicate prevention is intentionally left to the `Idempotency-Key` header instead. That means this header is the *only* thing standing between a network retry and a duplicate card.
**Decision:** The header is required on `POST /cards`, not optional. We implemented an idempotency middleware that hashes the request body deterministically and stores it in a dedicated table alongside the response.
**Rationale:**
- **Required, not optional:** A request without the header is rejected with 400 before it reaches any business logic. If it were optional, the one safeguard against duplicate card records could simply be skipped by not sending a header — that defeats the point of having it.
- **Deterministic hashing:** We sort the JSON keys before hashing, so `{"a":1,"b":2}` and `{"b":2,"a":1}` produce the same hash. This means the same logical request always maps to the same stored hash regardless of how the client serialized it, so a genuine retry is recognized as one.
- **Only a 2xx locks the key.** A completed, successful response is cached and replayed on retry — that's the whole point. Anything else releases the key immediately: a 4xx means the client sent bad input and should be free to fix it and retry the same key; a 5xx means the *server* failed, which is by definition transient, so caching it would make every retry after an outage replay the same stale error instead of actually trying again. We learned this the hard way in an earlier version, where 5xx responses were being cached as if they were final — fixed by only writing `status = 'completed'` on the 200-299 range.
- **Concurrent duplicate requests:** `INSERT ... ON CONFLICT (key) DO NOTHING` makes the first writer win atomically. If a second identical request arrives while the first is still `in_progress`, it gets a 409 telling it to retry shortly rather than racing the database.

## 5. Database Migrations (Defensive Raw SQL)
**Context:** We needed a way to manage schema changes without introducing a heavy ORM.
**Decision:** We implemented a plain SQL migration script that runs on startup (`src/db.ts`).
**Rationale:**
- **KISS:** A full ORM (like Prisma or TypeORM) adds unnecessary weight and complexity for a microservice with only two tables.
- **Idempotent by construction:** Every statement uses `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN IF NOT EXISTS`, so running it again on an already-migrated database is a no-op. That's what makes it safe for every ECS task to run it independently on boot instead of needing a separate one-shot migration step — with 2+ replicas starting at once, this has to be safe to run concurrently, not just repeatedly.
- **Known limitation:** if a statement in this script fails, we log the error but let the process boot anyway rather than crashing — so a broken migration currently degrades silently instead of stopping the deploy. Worth hardening later (fail fast instead), not done yet.
